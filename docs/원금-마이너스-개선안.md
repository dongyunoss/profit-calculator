## 2. 원금 산출 방식은 맞다 — 증명

`js/engine.js`가 쓰는 정의는 다음과 같다.

```
P (principal)  = Σ입금 − Σ출금            ← 보수·이익지급·재계약이 건드리지 않는다
성과 grossPnl  = 평가금액 + Σ보수 + Σ이익지급 − P
```

두 번째 식에 첫 번째 식을 대입하면

```
grossPnl = 평가금액 + Σ보수 + Σ이익지급 − (Σ입금 − Σ출금)
         = (평가금액 + Σ출금 + Σ보수 + Σ이익지급) − Σ입금
         = (계좌에서 나온 돈 전부 + 남은 돈) − (계좌에 넣은 돈 전부)
         = 진짜 순이익
```

**P가 음수여도 이 항등식은 그대로 성립한다.** 그래서 손지웅 기중현의 총성과
`10,821,407,138원`은 정확한 값이다. 분모가 음수인 것과 무관하게 **분자는 옳다.**

즉 `P`는 **원금이 아니라 순현금흐름**이고, 그 자리에서는 100% 제 역할을 하고 있다.

|---|---|---:|---:|
| 2025-12-26 | 입금 | 15,000,000,000 | 15,000,000,000 |
| 2026-02-06 | 입금 | 5,000,000,000 | 20,000,000,000 |
| 2026-03-17 | 성과보수 | 913,371,963 | 20,000,000,000 *(보수는 원금을 줄이지 않음)* |
| 2026-04-27 | 출금 | 2,400,000,000 | 17,600,000,000 |
| 2026-05-28 | 출금 | 9,200,000,000 | 8,400,000,000 |

**입금 200억, 출금 299.08억.** 99억을 더 받아 나온 것이고, 그건 계좌가 그만큼
벌었다는 뜻이다. 순현금흐름이 음수가 되는 건 **성공한 계좌의 정상적인 최종 상태**다.

> 참고로 마지막 출금이 잘못 입력됐다 하더라도 음수는 피할 수 없다.
> 그날 평가금액(161.46억)만큼만 출금했다고 가정해도 순현금흐름은 **−77.46억**이다.
> **음수는 데이터 오류가 아니라 산술의 결과다.**

## 4. 진짜 결함 세 가지

### 결함 ① — `principalReturn`에 부호 가드가 없다 *(명백한 버그)*

`js/engine.js`의 반환부에서 두 수익률의 처리가 다르다.

```js
contractReturn:  contractPrincipal > 0  ? contractPnl / contractPrincipal : 0,   // 부호 가드 있음
principalReturn: grossPrincipal !== 0 ? grossPnl / grossPrincipal   : 0,   // 0만 막고 음수는 통과
```

`contractReturn`은 `> 0`으로 막아서 음수 분모일 때 `0.00%`를 내보낸다.
`principalReturn`은 `!== 0`이라 **음수 분모를 그대로 나눈다.** 그 결과가 `−109.22%`다.

양수 분자를 음수 분모로 나눈 값은 수익률이 아니다. **의미가 없는 숫자이며 부호까지
뒤집혀 있어, 화면에서 "손실"로 읽힌다.** 이건 표기 취향 문제가 아니라 잘못된 정보다.

`js/engine.js`의 `computeSummary`에도 같은 구조가 있다.

```js
totalPrincipal += p.grossPrincipal;   // 음수 계좌가 그대로 합산되어 전체 분모를 깎는다
simpleReturn: totalPrincipal > 0 ? grossPnl / totalPrincipal : 0
```

전체 분모는 아직 양수(559.67억)라 부호가 뒤집히진 않았지만, **음수 계좌 2개가
전체 분모에서 130.09억을 상쇄해 전체 수익률을 부풀리고 있다.**

### 결함 ② — 순현금흐름을 "원금"이라 부른다

현재 화면에서 `원금`이라는 한 단어가 서로 다른 세 값에 붙어 있다.

| 화면 위치 | 실제 값 | 손지웅 기중현 |
|---|---|---:|
| 계좌 카드 "원금" | `contractPrincipal` (계약원금) | −913,371,963 |
| 상세 "원금" 부제 | `principal` (순현금흐름) | −9,908,035,175 |
| 원금 원장 마지막 행 | `principal` (순현금흐름) | −9,908,035,175 |
| — (화면에 없음) | 누적 입금액 | 20,000,000,000 |

**계약원금까지 음수(−913,371,963)로 표시되고 있다.** 보수 수취 시점(2026-03-17)에
계약원금이 평가금액으로 재설정된 뒤, 이후 출금 3건이 그보다 커서 음수로 내려간 것이다.
`contractReturn`은 가드 덕에 `0.00%`로 나오지만, **금액 자체는 음수 그대로 노출된다.**

### 결함 ③ — 좌수가 0이 된 뒤의 평가 입력이 통째로 버려진다 *(데이터 유실)*

두 계좌 모두 엔진이 경고를 **17건씩** 내고 있다.

```
2026-07-01 출금액(18,308,035,175원)이 평가금액(16,145,870,283원)을 초과합니다.
           좌수는 0으로 정리하고 원금만 전액 차감했습니다.
2026-07-01 좌수가 0인 상태의 평가금액 입력은 무시되었습니다.
2026-07-02 좌수가 0인 상태의 평가금액 입력은 무시되었습니다.
  ... (7-23까지 16건 더)
```

원인은 `withdraw` 처리부다.

```js
var subUnits = amount * NAV_BASE / nav;
if (subUnits > units + 1e-6) { warnings.push(...); subUnits = units; }  // 좌수는 0으로
units -= subUnits;
principal -= amount;                                                    // 원금은 입력액 전액 차감
```

좌수가 0이 되면 이후 `valuation`은 `if (units <= 1e-9) continue;`로 **전부 버려진다.**

실제로 어떤 일이 벌어지고 있나:

| 계좌 | 마지막으로 입력한 평가금액 | 화면 표시 |
|---|---:|---:|
| 손지웅 기중현 | 2026-07-23 · **257,181,814원** | 평가 2026-06-30 · **0원** |
| 손지웅 김여옥 | 2026-07-23 · **3,879,054원** | 평가 2026-06-30 · **0원** |

**7월 한 달간 매일 입력한 평가금액 34건이 저장은 되지만 계산에 전혀 반영되지 않는다.**
잔액 2.57억 / 388만원이 화면에서 사라진 상태다. 경고는 상세 패널에만 뜨고 계좌 카드에는
표시가 없어, 카드만 보면 눈치채기 어렵다.

또한 `isClosed`는 `closeout` 이벤트가 있어야만 참이다.

```js
isClosed: !!lastCloseoutDate && currentEval <= 1e-6,
```

두 계좌는 `withdraw`로 비워졌으므로 잔액이 0인데도 **"운용 중"으로 집계된다**
(헤더가 `운용 7 / 해지 0`).

### 5-2. 권장안 — 3단계

세 결함이 서로 독립적이라 따로 적용할 수 있다. 위험도가 낮은 순서다.

#### 1단계 · 부호 가드 (엔진 1줄 + 표시)

```js
// 분모가 0 이하이면 비율이 의미를 잃는다 — 계약 기준 수익률과 같은 규칙을 쓴다
principalReturn: grossPrincipal > 0 ? grossPnl / grossPrincipal : null,
```

`null`이면 화면은 `—`로 표시하고 그 자리에 **성과 금액을 대신 보여준다**
(`총성과 +10,821,407,138원 · 비율 산출 불가`). `0.00%`로 뭉개면 벌었다는 사실까지
지워지므로, 비율 대신 금액을 남기는 편이 낫다.

`computeSummary`의 `totalPrincipal`도 **음수 계좌를 상쇄에 쓰지 않도록** 바꾼다.

- **영향:** 손지웅 2계좌의 `−109.22% / −105.46%`가 사라진다. 나머지 5계좌 수치는 불변.
- **위험:** 거의 없음. 잘못된 값을 감추는 것뿐, 새 정의를 도입하지 않는다.

#### 2단계 · 이름 정리 (표시 문구만, 계산 불변)

| 지금 | 바꿀 이름 | 근거 |
|---|---|---|
| 원금 *(카드, `contractPrincipal`)* | **계약원금** | 보수·재계약으로 재설정되는 값임을 드러냄 |
| 원금 *(상세·원장, `principal`)* | **순현금흐름 (입금 − 출금)** | 음수가 정상임을 이름이 설명해 줌 |
| 원금대비 수익률 | **계약원금 대비** | 어느 원금인지 구분 |
| 원금흐름대비 수익률 | **투하원금 대비** *(3단계 후)* | 분모가 바뀌므로 함께 변경 |
| *(신설)* | **누적 입금액** | 손지웅 기중현 = 200억. 화면에 지금 없는 값 |

`누적 입금액`을 원장에 한 줄 추가하면 "그래서 원래 얼마 넣었는데?"가 바로 보인다.
`js/engine.js`가 이미 `totalDeposits`를 반환하고 있어 계산 추가는 필요 없다.

- **영향:** 계산 결과 변화 **0**. 문구와 표시 항목만 바뀐다.
- **위험:** 없음. `docs/계산식.md` 용어도 함께 맞춰야 한다.

#### 3단계 · 분모 교체 (엔진 변경 · 검토 필요)

`principalReturn`의 분모를 **기간가중 평균 투하원금**으로 바꾼다.

```
평균 투하원금 = Σ(구간별 순현금흐름 잔액 × 구간 일수) ÷ 전체 일수
```

- 자금이 실제로 계좌 안에 머문 기간만큼만 분모에 반영한다.
- 구조적으로 **항상 0 이상**이므로 음수 문제가 원천적으로 사라진다.
- 늦게 넣은 돈이 분모를 과대계상하지 않는다 → 토러스 기중현이 `23.74% → 52.43%`로
  올라가는 이유가 이것이다(입금 대부분이 후반에 들어왔다).
- 성과보수 지급의 기준으로도 이 쪽이 통상적이다.

**대안:** `Σ최대 투하원금`은 계산이 훨씬 단순하고 보수적이다(39.36%). "최대로 맡긴
돈 대비 얼마 벌었나"라는 질문에 답한다. 다만 자금을 뺐다 넣었다 한 계좌를 과소평가한다.

**어느 쪽이든, 대표 수익률은 이미 있는 `기준가 누적 성과(73.37%)`를 쓰는 게 맞다.**
현금흐름과 무관한 time-weighted 수익률이라 운용 실력을 재는 표준 지표이고,
지금도 정확하게 계산되고 있다. 투하원금 대비 수익률은 **보조 지표**로 두는 편이 좋다.

- **영향:** 전 계좌 `원금대비 수익률` 수치가 바뀐다(위 표 참고). 총성과 금액은 불변.
- **위험:** 중간. 과거에 보고한 수치와 달라지므로 **적용 시점을 정해야 한다.**

### 5-3. 데이터 정정 (코드와 별개 — 결함 ③)

7월 잔액이 화면에서 사라진 문제는 **입력 데이터를 고쳐야 풀린다.**

`2026-07-01` 출금 2건을 **실제 인출액으로 낮추고 잔액을 계좌에 남기면**, 그 뒤 7월 평가
34건이 정상 반영되고 경고도 사라진다.

| 계좌 | 현재 출금액 | 그날 평가금액 | 초과분 | 7-23 잔액 |
|---|---:|---:|---:|---:|
| 손지웅 기중현 | 18,308,035,175 | 16,145,870,283 | 2,162,164,892 | 257,181,814 |
| 손지웅 김여옥 | 8,100,825,167 | 7,813,341,084 | 287,484,083 | 3,879,054 |

**확인이 필요합니다:** 7월 1일에 실제로 인출한 금액이 얼마인가요?
계좌를 완전히 정리한 것이라면 `출금`이 아니라 **`전액출금(해지)`** 로 입력해야
`isClosed`가 정상 동작하고 헤더 집계도 `운용 5 / 해지 2`로 맞습니다.

코드 쪽으로도 재발 방지가 필요합니다.

1. **출금 초과 입력을 막는다** — 지금은 경고만 남기고 통과시킨다. 입력 시점에
   "평가금액(161.46억)을 초과합니다. 전액출금으로 처리할까요?"로 되묻는 편이 낫다.
2. **경고를 계좌 카드에도 노출한다** — 지금은 상세 패널을 열어야만 보인다.
   34건이 버려지는 동안 카드에는 아무 표시가 없었다.
3. **좌수 0 상태의 평가 입력을 버리지 않는다** — 무시하는 대신 그 금액을
   재개시 잔액으로 되살릴지, 입력 자체를 거부할지 정해야 한다. *(현재는 조용히 소멸)*
